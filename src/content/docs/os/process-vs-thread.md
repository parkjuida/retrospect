## 한 줄 요약

프로세스는 자원을 가진 단위, 스레드는 그걸 빌려 실행하는 단위.

## 처음 가졌던 질문

공부를 시작할 때 내가 알고 있던 것:

- 프로세스는 실행 중인 프로그램, 스레드는 프로그램이 점유하는 컴퓨팅 리소스를 가장 잘게 나눈 단위?
- 차이는 메모리 공유. 프로세스끼리는 메모리 공유가 안 되고, 같은 프로세스 안의 스레드끼리는 공유할 수 있다.

첫 번째는 절반만 맞았다. 스레드는 **자원**을 나눈 단위가 아니라 **실행**의 단위였다.

## 핵심 개념

### 자원의 단위 vs 실행의 단위

| | 역할 |
| --- | --- |
| 프로세스 | 자원 할당의 단위: 메모리, 열린 파일 등을 **가진다** |
| 스레드 | 실행(CPU 스케줄링)의 단위: 프로세스의 자원을 빌려 **일한다** |

비유하면 프로세스는 주방(재료, 도구, 냉장고), 스레드는 그 주방의 요리사다. 요리사가 늘어도 주방은 하나다.

스레드가 각자 갖는 것은 **스택, 레지스터 값, PC(Program Counter)** 뿐이다. 즉 "어디를 실행 중이고 어떤 함수를 거쳐 왔는지"라는 실행 흐름만 갖는다.

**스택을 따로 가져야 하는 이유**: 스택은 LIFO라서, 함수가 끝날 때 자기가 쌓은 데이터가 맨 위에 있어야 한다. 두 스레드가 한 스택을 쓰면 콜스택이 섞이고, 복귀 주소가 엉켜 엉뚱한 곳으로 점프한다. 코어가 하나라서 번갈아 실행하기만 해도 마찬가지다.

### 문맥 교환(Context Switch)

코어 하나는 한순간에 스레드 하나만 실행한다. 운영체제는 실행할 스레드를 바꿀 때 현재 스레드의 레지스터, PC, 스택 포인터를 저장하고 다음 스레드의 것을 복원한다.

| | 같은 프로세스의 스레드 전환 | 다른 프로세스로 전환 |
| --- | --- | --- |
| 레지스터, PC, 스택 저장/복원 | O | O |
| 주소 공간(페이지 테이블) 교체 | X | **O** |
| TLB(주소 변환 캐시) 무효화 | X | 대체로 O |
| CPU 캐시 | 계속 쓸 수 있음 | 캐시가 차갑게 식음 |

스레드 전환이 가벼운 이유는 주소 공간을 바꾸지 않기 때문이다. 저장/복원 작업 자체보다 **전환 뒤 캐시와 TLB가 비어서 느려지는 간접 비용**이 더 큰 경우가 많다.

### 사례: 크롬은 왜 탭마다 프로세스를 쓸까

스레드의 장점(공유, 가벼움)은 곧 약점(격리 없음)이다.

- **안정성**: 스레드 하나가 잘못된 메모리를 건드려 죽으면 프로세스 전체가 죽는다. 탭이 프로세스면 그 탭만 죽는다.
- **보안**: 스레드끼리는 메모리를 공유하므로, 악성 페이지가 다른 탭의 메모리를 읽을 여지가 생긴다. 프로세스는 운영체제가 하드웨어 수준에서 격리한다 (크롬의 Site Isolation).
- **자원 회수**: 문제 있는 탭 프로세스만 종료하면 그 메모리를 운영체제가 전부 회수한다.
- **대가**: 메모리를 많이 쓴다.

### 동기화: 메모리 공유의 대가

두 스레드가 `count = count + 1`을 각각 10만 번 실행하면 결과가 20만보다 작게 나온다. 이 한 줄이 CPU에서는 **읽기 → 더하기 → 쓰기** 세 단계로 쪼개지기 때문이다.

| 순서 | 스레드 1 | 스레드 2 | count |
| :-: | --- | --- | :-: |
| ① | 읽기: 레지스터 ← 5 | | 5 |
| ② | | 읽기: 레지스터 ← 5 | 5 |
| ③ | 더하기: 5 + 1 = 6 | | 5 |
| ④ | | 더하기: 5 + 1 = 6 | 5 |
| ⑤ | 쓰기: count ← 6 | | 6 |
| ⑥ | | 쓰기: count ← 6 | **6** (1이 사라짐) |

- **경쟁 상태(race condition)**: 실행 순서에 따라 결과가 달라지는 상황
- **임계 구역(critical section)**: 공유 자원을 건드리는 코드 구간
- **뮤텍스(mutex)**: 임계 구역에 한 번에 한 스레드만 들어가게 하는 락

```c
lock(&m);
count = count + 1;
unlock(&m);
```

락의 대가는 세 가지다.

1. **오버헤드**: 락을 잡고 풀 때 원자적 명령이 필요하고, 락을 못 잡은 스레드는 잠들었다 깨어나며 문맥 교환이 생긴다.
2. **병렬성 상실**: 락 구간은 한 줄로 서서 실행된다. 락이 넓으면 코어가 많아도 소용없다.
3. **교착 상태(deadlock)**: 서로 상대가 가진 락을 기다리며 영원히 멈춘다.

그래서 락은 **꼭 필요한 곳에만, 가능한 한 짧게** 건다.

## 직접 해보기

스레드와 프로세스에서 각각 전역 리스트를 수정하고, 원래 프로그램에서 그 변경이 보이는지 확인한다.

```python
import threading
import multiprocessing

data = []

def work():
    data.append("hello")

if __name__ == "__main__":
    t = threading.Thread(target=work)
    t.start(); t.join()
    print("스레드 실행 후:", data)

    data.clear()
    p = multiprocessing.Process(target=work)
    p.start(); p.join()
    print("프로세스 실행 후:", data)
```

```
스레드 실행 후: ['hello']
프로세스 실행 후: []
```

스레드는 같은 주소 공간을 쓰니까 변경이 보이고, 자식 프로세스는 자기만의 주소 공간에서 수정했으니까 부모에게는 보이지 않는다.

## 헷갈렸던 포인트

- **스레드는 "리소스를 가장 잘게 나눈 단위"가 아니다.** 자원은 프로세스가 갖고, 스레드는 실행 흐름(스택, 레지스터, PC)만 갖는다.
- **프로세스끼리도 메모리 공유는 할 수 있다.** 기본값이 격리일 뿐, IPC(공유 메모리, 파이프, 소켓 등)로 운영체제에 요청하면 된다.
- **동시성 ≠ 병렬성.** 동시성은 번갈아 진행되어 동시에 되는 것처럼 보이는 것(코어 1개로도 가능), 병렬성은 물리적으로 같은 순간에 실행되는 것(코어 여러 개 필요).
- **프로세스로 나눠도 "느려짐"은 못 막는다.** 탭이 별도 프로세스여도 같은 CPU와 RAM을 나눠 쓴다. 프로세스 격리가 막아주는 건 크래시 전파와 메모리 침범이다.

## 복습 퀴즈

<details>
<summary>Q1. 같은 프로세스의 스레드들이 공유하지 않고 각자 갖는 것 세 가지는?</summary>

스택, 레지스터 값, PC(Program Counter).

</details>

<details>
<summary>Q2. 스레드 전환이 프로세스 전환보다 가벼운 이유는?</summary>

같은 주소 공간을 쓰므로 페이지 테이블을 바꿀 필요가 없고, TLB와 CPU 캐시를 계속 활용할 수 있기 때문.

</details>

<details>
<summary>Q3. 크롬이 탭마다 프로세스를 쓰는 이유는? 그래도 해결되지 않는 문제는?</summary>

크래시 격리(탭 하나가 죽어도 브라우저는 유지), 보안(다른 탭 메모리 접근 차단), 자원 회수(탭 단위로 종료). 하지만 CPU와 RAM은 여전히 공유하므로, 무거운 탭이 다른 탭을 느리게 만드는 건 막지 못한다. 대가로 메모리를 더 쓴다.

</details>

<details>
<summary>Q4. 두 스레드가 count = count + 1 을 10만 번씩 실행하면 결과가 20만보다 작은 이유는? 락을 걸면 치르는 대가는?</summary>

한 줄이 읽기 → 더하기 → 쓰기로 쪼개져서, 두 스레드가 같은 값을 읽고 각자 쓰면 증가분 하나가 사라진다(경쟁 상태). 락의 대가는 오버헤드, 병렬성 상실, 교착 상태 위험.

</details>
